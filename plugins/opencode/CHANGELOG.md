# Changelog

## 0.2.0

- CI runs on an ubuntu + macOS matrix and also syntax-checks every runtime file and smoke-tests `setup --json`, rather than running the unit tests on Linux only. The runtime's platform-sensitive parts — process groups, signal handling, atomic rename, lock files — are exactly the ones a single-OS matrix does not cover, and this plugin is developed on macOS.
- `setup` reports leftover `.opencode-plugin-codex` / `.grok-plugin-codex` / `.opencode-plugin-cc` directories in the working tree (in `--json` as `legacyStateDirs`) and says they are safe to delete. These are 0.1-era job stores written into the user's own repository — the user asked for them to be gitignored at the time, one was still present a month later, and a sibling project's lint run failed on it. They are reported, never deleted: this is the user's working tree.
- The review target selector now covers what callers actually ask for. `--base` accepts a plain ref *or* a range written as `A..B` / `A...B`; `--head <ref>` moves the other end (default HEAD) and is only meaningful alongside `--base`, so on its own it is refused rather than falling through to a working-tree review of whatever happens to be dirty; `--paths <glob,...>` (alias `--files`) limits the review to a file set; free focus text is accepted by `review` as well as `adversarial-review` instead of being dropped; and `--rubric-file <path>` supplies the caller's own severity vocabulary while the JSON schema stays fixed. `review` and `adversarial-review` were used **zero** times in two months of recorded use while every real request was a commit range plus a document set — `git diff 71dcdc5..HEAD`, "the documents under docs/, committed" — which the old `working tree | <base>...HEAD` selector could not express, so callers rebuilt reviews in ad-hoc prompts and got mutually incompatible output shapes. Input truncation is also a `review_input_truncated` warning now, carrying the real and truncated sizes, instead of a sentence inside the prompt that only the model saw. And a target with no changes in it answers `--json` callers in JSON: `{"ok": true, "outputState": "empty", "outputStateReason": "nothing-to-review", "isEmpty": true, "label": "<target>", "review": null, …}` with the same keys a real review returns, exit code still 0. It used to print `Nothing to review: …` on stdout and exit 0 whatever the caller asked for, which left a `--json` consumer with neither a document to parse nor a code to branch on — on the most benign path there is (a clean tree, a path filter that matched nothing). The human channel keeps the sentence.
- `adversarial-review` takes `--threat-model "<boundary>"`, and the prompt now requires every finding to be labelled `in-model` or `out-of-model` against it. An out-of-model finding is advisory: it cannot produce `needs-attention`, and the result-handling skill forbids letting one interrupt work already in flight. Without the flag the reviewer is told to assume a single-user local application with no network exposure rather than an unstated hostile one. The prompt's vocabulary also drops `attacker` / `malicious` / `attack chain` / `attack_surface` in favour of failure and breakage language — the same wording pattern tripped a sibling runtime's `cyber_policy` filter and killed a user's task mid-run. This follows the user's own instruction, recorded twice: security findings outside the system's actual exposure must not interrupt their work.
- There is now a stable entry point. The SessionStart hook exports `OPENCODE_COMPANION_BIN` (the absolute path of the copy that is actually running, resolved from the script itself), and the rescue skill and agent invoke `${OPENCODE_COMPANION_BIN:-${CLAUDE_PLUGIN_ROOT}/scripts/opencode-companion.mjs}` instead of a bare plugin-root path. They also ban versioned cache paths and `find | head -1` outright: an orchestrator that hard-coded `.../opencode/0.1.0/scripts/...`, then guessed, then searched, ran a stale copy for 3.5 hours while its job state went to another plugin's directory. `--help` now prints the plugin version, the file it is running from and the resolved job store; `setup --json` reports `pluginVersion` and `companionPath`; the job handle carries `companionVersion`; and a newer install sitting next to the running one produces a stderr warning naming it.
- `status --json` now reports `elapsedMs` and `resultComplete` for every job, and the single-job form returns `resultComplete` alongside `hasResult`, so a scheduler can fence on several opencode jobs with one call instead of one call per job plus a `result` read. The result-handling skill documents which call to use and what its fields mean; the measured wall times to budget against (median ~3 min, p90 ~5.5 min for read-only reviews on the plan agent) live in `status --help` and the README, where scheduling guidance belongs. A 2-minute wait is below this runtime's median, and 16 of 19 recorded three-way aggregations had an empty opencode slot because the answer arrived after the decision point.
- `result` gained `--structured-only` (print just the review JSON object; exit 1 with the reason when the run never produced one) and no longer prints a bare blank line for an empty payload — `String(x).trim() ?? "[no output stored]"` could never reach its placeholder, so "the job stored nothing" and "the store could not be read" looked identical. `commands/result.md` and the result-handling skill now say to feed scripts with `--json` or `--structured-only` and never to slice the rendered text with `head -c` / `tail -c`, which breaks multi-byte characters and embedded JSON. There is still no output cap and no truncation flag, on purpose: this command's contract is that its output is relayed verbatim.
- Runs now record and display the model that actually ran. Every job in the recorded corpus stored `model: null` and no renderer showed the agent, while this plugin's read-only runs (every `review`, every `adversarial-review`, and `task` without `--write`) go through opencode's `plan` agent — so they run on whatever `agent.plan.model` says, which in the observed config is a flash-tier model. That was a side effect of an agent name that nobody had chosen, and it was invisible in the output people were using as an implementation gate. The job record now carries `model`, `requestedModel`, `modelSource`, `agent` and `variant`; the footer and `status <id>` print `Model: <provider/model> (agent plan, variant max)`; a `read_only_model_override` warning fires when the agent's model differs from the configured default and no `--model` was given; and `setup` reports `readOnlyModel` alongside `defaultModel`. The config reader is a real JSONC parse of the specific keys instead of the first `"model": "…"` substring in the file, which in a per-agent config returned whichever entry was written first. It reads the project's own `opencode.json` / `opencode.jsonc` (nearest one, walking up from the working directory) on top of the global file, the way opencode resolves them — reading only `~/.config` reported the wrong model, confidently, in exactly the repositories that pin their own. And because opencode has the final say, the distinction between observation and inference is now visible rather than assumed: `--model` (which this plugin puts on the command line) and a model id reported by the run's own event stream are reported as `Model: <id>`; a value inferred from config prints `Model (expected): <id>` and carries `modelCertainty: "expected"` next to `modelSource`. `setup --json` also lists the `modelConfigFiles` the numbers came from. `model`, `modelSource`, `modelCertainty`, `agent` and `variant` are on the `--json` document of `task`, `review` and `adversarial-review` too, not only on the job record behind `status`/`result` — a caller branching on `modelCertainty === "actual"` straight from `task --json` used to read `undefined`. `review --json` / `adversarial-review --json` also carry `jobId` now, the way `task --json` always has; the empty-target document carries the same keys as `null`. The single-job `status <id> --json` and `result [<id>] --json` documents carry a top-level `jobId` too, so `doc.jobId` reads the same across all four — it used to be reachable only as `doc.job.id`, and `result` without an id resolves the newest finished job, so the id it settled on was the one thing the caller could not otherwise know.
- The Stop hook's "opencode job `<id>` is still running" reminder is now a non-blocking hook payload (`systemMessage`) instead of a stderr line. It went to a channel that reaches neither the model nor the transcript — 348 recorded Stop records carry empty hook content — which means the one signal that could have caught unreclaimed jobs before a session ended was being written where nobody reads it. The hook also returns after a single `existsSync` in a workspace that has never run this plugin: three of these hooks (grok / opencode / codex) fire on every Stop, and the gate was enabled in none of 25 recorded workspaces.
- **Contract change.** The optional stop-time review gate now fails open, breaks loops, and stops paying for empty rounds. (1) `stop_hook_active` is honoured — Claude Code's standard loop breaker was not read anywhere in the repo, so the gate had no circuit breaker at all — and a session that is blocked twice in a row makes the gate stand down with an explanation instead of a third block. (2) Only an explicit `BLOCK:` verdict blocks now. The infrastructure paths (the task could not be started, the deadline passed, no document to parse, no output, an answer in an unrecognised format) allow the stop and print `opencode stop-gate could not complete (<reason>); allowing the stop. Run /opencode:review --wait manually.` — this runtime's most common outcome used to be a *blocked stop caused by the gate's own failure*. This weakens the guarantee on purpose: for a hook whose failure mode is "the user cannot end the session", unreliable blocking is worse than honest non-blocking. The verdict is read out of the child's `--json` payload rather than from its exit status, and the child runs with `OPENCODE_COMPANION_MIN_ANSWER_CHARS=0`: this gate's contract asks for one short line, so a reviewer that read the repo before saying `BLOCK: <reason>` used to classify as narration, exit 2, and be waved through as "the review never ran" — fail-open on the gate's only intended path. (3) Before spawning anything the gate asks git whether there is a diff at all, and skips the review when the working tree is clean *and* HEAD has not moved since the previous stop. (4) The inner review deadline is now 80% of the `hooks.json` Stop budget (720s of 900s) rather than exactly equal to it, so the friendly timeout message can actually be delivered, and the readiness probe (~1.1s of `opencode --version` + `opencode auth list`) runs once per stop instead of twice.
- `task --resume-last` and `task-resume-candidate` now use one selection rule (`pickResumeCandidate`). They disagreed: `--resume-last` continued the most recently updated job of *any* kind and *any* status — a stale `running` review could win — while the candidate query the rescue command shows the user before asking for approval filtered to completed tasks, so the session the user approved was not necessarily the one that ran, and the resume printed nothing to make that visible. The shared rule prefers the current Claude session, then the newest resumable task: `completed`, `incomplete` (resuming an unfinished run to ask for the final answer is the documented recovery) or `failed`, never `cancelled` or `failed (orphaned)`. A successful resume now prints `Resuming opencode session <id> (from job <id>: <prompt>)` and `--json` carries `resumedFrom: {jobId, opencodeSessionId}`. Both that line and the `No previous opencode session found for this repository; starting a fresh run.` notice go to **stderr** under `--json`, so stdout stays one JSON document even in a repository that has never run a job. New `task --resume-session <ses_id>` continues exactly one named session with no heuristic at all — `/opencode:rescue` now forwards the id it just showed the user.
- `review` and `adversarial-review` no longer swallow arguments. `--model` and `--variant` are accepted and forwarded to the run (README has been teaching `/opencode:review --model …`, which silently produced a default-model review); an unknown flag before the free text fails the command with the list of supported flags instead of landing in `rest`, where only the adversarial path ever looked; `--scope` is validated against `auto|working-tree|branch`, so the documented-as-unsupported `staged` / `unstaged` no longer fall through to a working-tree review that then gets relayed as authoritative; and `--threat-model` is refused by plain `review` with the same list, because only the adversarial prompt has a slot for it — it used to sit in the shared flag spec, escape the unknown-flag check, and then be discarded during interpolation. (Free focus text, which `review` also used to drop, is now a real input: see the target-selector entry above.) `status` and `result` read the same parse result: a value flag that lost its value (`status <id> --wait --timeout-ms`) is refused with `Invalid arguments: --timeout-ms requires a value` instead of reading as unset, falling back to the 15-minute default and blocking for it; a mistyped flag is named instead of being taken for a job id. `transfer` does too: `--source` with no value used to read as unset and fall through to the transcript the SessionStart hook exported, so the handoff ran anyway — one model turn spent on a different session than the caller named.
- **Contract change.** Structured review output is now validated against `schemas/review-output.schema.json` before it is believed. `renderReviewOutput` accepted any object, so a model that gave up mid-review with `{"note":"I could not finish"}` was rendered as a verdict with an empty summary and "No material findings." — a clean review nobody wrote — and the upstream extractor will lift a JSON fragment out of narration to get there. A review whose final answer has no JSON object, or one that fails required-key / `verdict` enum / `findings` shape checks, is now `incomplete` (`outputStateReason: "schema-mismatch"`, exit code 2, `review: null` in `--json`), renders the raw text with the specific mismatches listed and no synthesised verdict, and points at a resume that asks for the JSON object only. Unknown extra keys are still accepted: they are not a reason to discard a well-formed review.
- Failed runs are now classified. `classifyFailure` reads the stderr tail and labels the job `model_unauthorized`, `model_not_found`, `quota_exhausted`, `auth_required`, `rate_limited`, `provider_error` or `opencode_failed`; the class lands on the job record (rendered as `failed (<class>)`), in `task`/`review` `--json` as `failureClass`, and as one `Next step (<class>): …` line printed *above* the unchanged stderr block. The classification never moves the pass/fail verdict — a misread tail costs a wrong suggestion and nothing else. It matters most for `quota_exhausted`, which callers were retrying as if it were a transient plugin fault, and for `rate_limited` (429 / rate limit / overloaded), which is the opposite case: genuinely transient, worth re-running unchanged, and previously indistinguishable from "no recognised reason". The evidence is the stderr tail **only** — opencode's own answer used to be half the haystack, so a run that failed after writing a sentence about an HTTP code took its class from its own prose — and an HTTP code has to travel with matching context: a bare `403` is what git says about a private remote, not a model authorisation error, and `Did you mean` only means a missing model when it names one (`aihubmix/gpt-5`). The result-handling skill lists the same class names and which of them are worth a retry.
- **Contract change.** Runs are now classified three ways instead of pass/fail. A run that exits 0 without producing an answer is `incomplete`, not `completed`: empty final text, a stop reason that is not a finished turn (`tool-calls`, `length`, `aborted`, …), or a very short final message after tool calls on a large prompt. `incomplete` runs exit with code **2** (failures keep 1), get the job status `incomplete`, and render through a dedicated renderer that labels the partial output as work-in-progress, prints the tail of stderr (which is where opencode reports auto-rejected paths), and gives a `/opencode:rescue --resume` recovery command. `task`/`review` `--json` now include `outputState`, `outputStateReason`, `stopReason` and `toolEventCount`; `status`/`result` detail show the output state and stop reason. Unknown stop reasons only warn on stderr — they never downgrade a run. The narration heuristic threshold is `OPENCODE_COMPANION_MIN_ANSWER_CHARS` (default 200).
- **Contract change.** Job records are reconciled against process liveness whenever they are read (`status`, `result`, `cancel`, the Stop and SessionEnd hooks). A `running`/`queued` record whose child pid is gone — or that never recorded one and has been untouched for longer than the 120s grace window — is rewritten as `failed` with `failureClass: "orphaned"`, an end timestamp, and elapsed time frozen at the last sign of life instead of growing forever. `status`/`result` render it as `failed (orphaned)` and point at the job log plus `/opencode:rescue --resume`; `status --wait` now returns as soon as a job reaches a terminal state instead of polling a dead record for the full 15 minutes. Reconciliation only relabels — killing processes stays with `cancel` and session teardown.
- **Contract change.** `task`, `review` and `adversarial-review` no longer swallow `--background`: they exit 1 with `--background is a Claude Code execution flag, not a companion flag; the companion always runs in the foreground. Detach with Bash(run_in_background: true), or use /opencode:rescue --background.` Passing it used to look like a successful detach while the run was still on Claude Code's 2-minute Bash wall that then killed it. `--wait` stays an accepted no-op — the companion is a foreground runner, which is what it asks for. The two review slash commands now strip both flags before building the companion command line.
- `task`/`review`/`adversarial-review` accept `--timeout-ms <ms>` (default 900000). `opencode run` has no timeout flag of its own, so this is the only deadline a stuck run has: at the deadline the companion terminates the child's process group and records `failed` with `failureClass: "timeout"`, and the failure render says how long it waited. `result` accepts `--wait` and `--timeout-ms` (default 900000), blocking until the job reaches a terminal state and then printing the same output — the primitive the hand-written `for i in $(seq 1 180)` polling loops were emulating. `--help` now lists `--timeout-ms` and states that `--background`/`--wait` are Claude-side flags.
- `--help` / `-h` is now handled per subcommand and intercepted before dispatch, so `task --help` prints the companion's own flags instead of being forwarded to opencode as the prompt. It used to cost a real model turn and come back as a *model-generated* help page for the opencode CLI — describing flags this companion has never had — and one of those runs was stored as a `completed` job. A `--flag` that appears before any free text and is not in the subcommand's spec now fails the run (`Unknown flag: --wrote. Run 'task --help' for supported flags.`) instead of being sent as prompt text; dashes *inside* task text stay task text, and a `--` that arrives before any free text ends flag parsing so anything after it is literal. That sentinel is positional now, like the unknown-flag rule beside it: a standalone `--` that appears once the task text has started is part of the text. It used to be consumed wherever it stood, so `task "run the suite -- then report"` reached opencode as `run the suite then report` — a different instruction that still reads as English, with nothing in the output to show a word had been deleted.
- The companion now handles `SIGTERM`/`SIGINT`/`SIGHUP`. It had none, and opencode is spawned detached, so a Bash timeout killed the companion and left the opencode child running (one 2026-07-17 incident needed `kill -9` on two pids by hand) with the job record frozen at `running` and nothing stored. The handler kills the child's process group, records `failed` with `failureClass: "interrupted"`, stores whatever opencode had streamed so far so `/opencode:result <id>` still shows the partial output, and then re-raises the signal with its default disposition so the exit status stays truthful (143 for SIGTERM). It never overwrites a job that already reached a terminal state, so it is idempotent with `cancel` and session teardown.
- `task`, `review` and `adversarial-review` print the job handle *before* opencode starts (`Job: <id> (task, running) — poll with /opencode:status <id>`; a JSON line on stderr under `--json`, so stdout stays a single document). The id previously appeared only in the footer after the run, so the 28 recorded runs that were detached with `Bash(run_in_background: true)` had no handle to poll while they were in flight and grew hand-written shadow job control instead.
- `task` gained `--prompt-file <path>` and `--prompt-stdin`, and in the single-argument form everything after a standalone `--` is now passed through byte for byte instead of being tokenized. The documented `task "<prompt>"` shape ran the prompt through a tokenizer that drops quote characters, truncates at an apostrophe and folds newlines into spaces — 8 of 39 recorded `task` calls used exactly that shape, all of them carrying quoted, multi-line review contracts. Passing both a prompt source and free text is now an error rather than a silent drop. The rescue skill and agent document `-- <prompt>` and `--prompt-file` as the supported forms.
- An auto-rejected opencode permission is now a typed warning instead of a line the caller had to notice in the stderr tail. `! permission requested: external_directory (<path>); auto-rejecting` becomes `external_path_blocked: opencode refused to read <path> because it is outside <cwd>. Copy the file into the repo, or inline its contents in the prompt.`, printed above the stderr block in every renderer, on stderr, and in `--json` as `warnings[]`. The `opencode-prompting` skill now forbids referencing absolute paths outside the repository root outright — Claude Code stages material under `/private/tmp/claude-501/.../scratchpad`, which opencode will never read.
- The rescue forwarder no longer returns nothing when it fails. `agents/opencode-rescue.md` and `skills/opencode-cli-runtime/SKILL.md` told it to stay silent if the Bash call failed — which is exactly the case where it has no stdout to return, so 6 of 13 recorded rescue dispatches came back with no opencode answer while their job had already completed. The rules now split along "independent work" vs "retrieving my own result": self-authored answers, retries and repo inspection stay banned, while the forwarder must keep the job handle, may retrieve that one job with a bounded number of `status`/`result` calls, and otherwise must return the single line `OPENCODE_RESCUE_FAILED: <reason> | job=<id> | log=<path>`. The result-handling skill says what to do with that line.
- The event stream is now scanned for interactive skill loading (`skill` tool calls and reads of a `SKILL.md`). When a run loaded any, the job payload and `--json` carry `skillsLoaded[]` and a `skills_loaded` warning names them and says a repository bootstrap file is probably overriding the plugin's headless preamble. 89 of 231 recorded opencode job logs opened by loading a workflow skill rather than doing the requested work; that cost was previously invisible in both the answer and the job record.
- Review verdicts now carry the evidence behind them. `review`/`adversarial-review` report `evidenceLevel` (`none` | `thin` | `substantive`, derived from tool-call count) next to the verdict and in `--json`, and a verdict produced with zero tool calls gets a `no_evidence_review` warning saying it can only be defended for what the inlined diff shows. Both review prompts now require an `approve` summary to state what was actually inspected, and the result-handling skill says an evidence-free approval is no signal rather than a passing vote. (30 of 64 recorded "succeeded" review jobs in the sibling runtime had opened no file at all.) The same judgement is machine-readable as `resultComplete` in `--json` and in the stored payload — `false` for a zero-evidence review and for any run that did not finish — so an orchestrator can discard such a verdict without parsing warning text. It is a separate field from `outputState` on purpose: the run did complete, and merging the two would make "produced no answer" and "answered without looking at anything" the same value.
- **Contract change.** The job store no longer falls back to `CLAUDE_PLUGIN_DATA`. That name holds whichever plugin's SessionStart hook ran last in a given shell, so any Bash context that had not sourced the session env file silently used another plugin's directory — the 0.1.1 fix only made the namespaced variable *preferred*, and opencode job logs were still landing under `codex-inline/state/...`. Resolution is now `OPENCODE_COMPANION_DATA_DIR` or the temporary fallback, and the fallback announces itself on stderr (never stdout) on every command that touches the store. `state.json` also carries `{"owner": "opencode-plugin-cc"}`: a store stamped by another plugin is refused with a message naming both owners instead of being read or overwritten, while a pre-stamp file is adopted on the next write. `status --json` and `setup --json` report the resolved `stateDir` and its `stateSource`, and "No job found with id X" now also prints the workspace root, the store path and the id/kind/status of up to five recent jobs (never prompt text).
- The prompt templates the plugin builds (`prompts/review.md`, `prompts/adversarial-review.md`, `prompts/stop-review-gate.md`) now open with a headless-delegation preamble: ignore repository bootstrap rules that tell the delegate to load interactive skills or personas (`pua`, `superpowers`, …) before working, and do not narrate steps. Headless delegates obeyed those rules faithfully — a large share of recorded jobs spent their first turns reading a workflow SKILL.md instead of the work — which fed both the turn-budget and timeout failure classes.
- `task` output now prints the last 5 lines of stderr on successful runs too, not only on failed and incomplete ones. opencode reports an auto-rejected read of a path outside the repo (`! permission requested: external_directory (/private/tmp/*); auto-rejecting`) on stderr and still exits 0, so the cause of a thin or missing answer used to be invisible to the caller — and Claude Code stages large prompts and material in `/private/tmp/claude-501/.../scratchpad` by default.
- Terminal job writes (`task`/`review` verdicts, `cancel`, session teardown) now clear `failureClass`, and a failure label is only ever rendered next to a `failed` status. Reconciliation runs from every reader, so a job could be relabelled `failed (orphaned)` while its own companion was still parsing the run; the record then ended up `completed` *and* `orphaned`, and `status`/`result` printed "the companion process for this job died" underneath a real answer. The child pid is also dropped as soon as opencode exits, so the parse-and-render window runs on the grace clock instead of pointing at a dead process.
- `state.json` and job payload files are now written to a temp file and renamed into place. An in-place overwrite let a concurrent reader see a half-written file, and both `loadState` and `readJobFile` swallow a parse failure — so a torn read silently became "this repository has no jobs" / "no stored output for this job". The read-modify-write around that rename is now serialised too, on an advisory `O_EXCL` lock file next to the store: two companions calling `upsertJob` at the same instant used to both merge into the same snapshot, and the loser's record was reverted to whatever the winner had read — a job that `findJob` can no longer see, so `result <id>` denied a run whose payload was on disk. Measured with 8 concurrent writers: 3 of 8 records kept their final status before, 7 of 8 with the bounded re-merge that is still there as a fallback, 8 of 8 now. The lock cannot wedge anything: one left behind by a killed writer is broken after 5s, and a writer that still cannot take it after 10s proceeds without it rather than failing a job write.
- `saveState` now unions the caller's snapshot with what is on disk before deciding which jobs to prune, so a concurrent writer's job record, stored payload, and open log file can no longer be deleted by a companion holding a stale snapshot.
- Rescue docs (`skills/opencode-cli-runtime/SKILL.md`, `agents/opencode-rescue.md`) now ship explicit `Bash` invocation templates with `timeout: 600000` and a `run_in_background: true` variant for long runs. Forwarders previously inherited Claude Code's 120s default, which killed 16% of `task` calls with `Exit code 143` mid-run.

## 0.1.1

- State resolution now uses the namespaced `OPENCODE_COMPANION_DATA_DIR` env var instead of trusting `CLAUDE_PLUGIN_DATA` from the shared session env, where the last plugin's SessionStart hook to run wins (e.g. the Codex plugin exports it too). Fixes job state landing in another plugin's data directory.

## 0.1.0

Initial release, ported from the Codex plugin for Claude Code (and its Grok port) to the opencode CLI.

- `/opencode:rescue` task delegation with resume, model/variant selection, and background jobs
- `/opencode:review` and `/opencode:adversarial-review` with structured JSON findings
- `/opencode:status`, `/opencode:result`, `/opencode:cancel` job management
- `/opencode:transfer` Claude-session handoff into a seeded opencode session
- `/opencode:setup` readiness report and optional stop-time review gate (Stop hook)
- Session lifecycle hooks that expose the Claude session to the runtime and tear down orphaned jobs
